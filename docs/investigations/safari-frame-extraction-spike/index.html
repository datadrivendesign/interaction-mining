Safari frame extraction spike

Extracts the same timestamps two ways and compares them: the current pipeline (drawImage from a <video>), and ffmpeg.wasm. Each frame is reduced to a 36-point signature. If a method returns the same signature for different timestamps, that method is handing back one frame regardless of position — the failure being investigated (WebKit 153588). Run it in Safari, on a real iOS capture recording.

Input

Leave the spread blank to sample the whole recording — that is the run that catches a read stuck on one frame. Set it to 0.6 to cluster the samples a couple of frames apart instead, which checks that ffmpeg decodes to the exact timestamp rather than snapping to keyframes. Both need to pass.
For the clustered run, centre it on a moment where the screen is actually moving — a scroll or a transition. Half a second of a static app screen yields identical frames honestly, which looks exactly like a broken read and cannot be told apart from one.
